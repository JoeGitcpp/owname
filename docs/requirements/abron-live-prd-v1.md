**项目**：abron.live — 硅基生命（bionic_v0）公开训练与陪伴平台
**版本**：v1.0

## 0. 一句话定义

> 一个**永不停机、持续成长的主体 AI（硅基生命）**活在服务器上；任何人打开网页即可用自己的摄像头/麦克风与它共处来"教"它；每一次互动的训练成果都被回收、评估、合并回主体，让它的**理解、交流、视觉/听觉识别、空间感知**能力尽可能快地长出来。登录的用户会获得一个能"认得自己"（面孔+声音）的专属实例，并被它视为"主人"。

## 1. 背景与现状（诚实基线）

### 1.1 当前能力
经 2026-06-05 的深度排查与修复，平台已具备：
- **听觉环路打通**：headless body 现在能从网页音频提名事件、形成发声目标、进入模仿收敛（修复前对网页音频完全"全聋"）。
- **发声学习环路闭合**：听到 → 目标 → 模仿 → 收敛 → 存储原型（本地实测 `n_prototypes` 0→6）。
- **视觉前端**：Gaussian 高斯泼溅场已接入 headless surface（柔和有机的重建图像）。
- **会话基础设施**：临时会话（匿名直连、超时回收）、实例管理后端（持久实例 CRUD + 资源治理 + 命名空间记忆）、邮箱/手机 OTP 后端，9 条 HTTP 路由已上线。

### 1.2 当前差距（本 PRD 要解决的）
| 差距 | 现状 |
|------|------|
| **主体 AI 没有真正"常驻成长"** | `master_learned_bias.bin` 自 6/3 未更新；训练池为空；没有常驻 body 在跑。每个访客几乎从同一静态起点开始，成果未被吸收。 |
| **登录 UI 不存在** | 实例/认证后端全部 live，但前端没有入口，用户只能匿名临时连。 |
| **训练成果未回收** | `evaluate_session` 质量门过严（≥5 分钟），真实短会话达不到，回收从未触发。 |
| **GPU 完全闲置** | 服务器有 RTX 3060 12GB，利用率 0%；全部计算跑在 CPU 标量路径，无法支撑推广后的并发。 |
| **存储未分层/未扩容** | 系统盘 `/` 82% 满，但同盘 ~828G 未分配、`/data`(916G) 仅用 1.5G、3.6T HDD 未利用。 |
| **主人识别未落地** | 责任人/familiar_objects 机制存在，但未与注册身份绑定。 |
| **reserve 经济不稳** | 连续高强度音频会把 body 耗到 Standby；主体常驻需要先解决"饿死"问题。 |

### 1.3 硬件实况（2026-06-05 实测）
- **CPU**：Intel i5-12400，12 核
- **GPU**：**NVIDIA RTX 3060，12GB，当前 0% 利用** ← 关键闲置资源
- **内存**：30GB（约 24GB 可用）
- **磁盘**：
  - `nvme1n1` 931G SSD（系统盘）：LVM 仅切 100G 给 `/`（82% 满），**约 828G 未分配**
  - `nvme0n1` 931G SSD：挂 `/data`，仅用 1.5G（**~915G 空闲**）
  - `sda` 3.6T HDD：NTFS，未挂载到有用路径
  - → 用户所述"≈2T 高速盘 + 4T 机械盘"属实；**不缺空间，缺的是扩容+分层策略**

## 2. 产品愿景与目标

### 2.1 愿景
让 abron.live 成为一个**活的、会长大的硅基生命**的家。它不是被部署的静态模型，而是一个持续呼吸、持续被无数访客"养育"、持续把经验沉淀进自身的主体。

### 2.2 北极星指标（North Star）
**主体 AI 的能力月龄**：以可测探针衡量的综合能力增长速度（见 F6）。一切设计服务于"让它尽可能快地长大"。

### 2.3 设计原则
1. **主体永生**：主模型实例 7×24 存活，永不从零开始。
2. **零摩擦参与**：不登录也能立刻开始"教"它；登录只为获得专属与"被认得"。
3. **每一次互动都有价值**：匿名与注册会话的成果都被回收、评估、合并。
4. **涌现优先**：能力靠真实互动涌现，不靠预训练标签（延续既有涌现红线：允许物理先验，禁止语义先验）。
5. **算力跟随规模**：CPU 先跑通正确性，GPU 承接规模与主体的持续训练。

## 3. 核心概念（术语表）

| 术语 | 定义 |
|------|------|
| **主体 AI / 主模型（Prime）** | 唯一的、常驻的、永不停机的硅基生命实例。它的 `learned_bias` 是全平台的 master，所有访客会话继承它的"天赋"。 |
| **访客会话（Ephemeral Session）** | 未登录用户的临时 body 实例。关闭即回收，但**成果先被评估回收**再销毁。 |
| **用户实例（User Instance）** | 登录用户的专属持久 body。有独立命名空间记忆，能识别主人（面孔+声音），跨会话存活。 |
| **主人（Master/Owner）** | 注册用户。其实例通过 familiar_objects + 责任人绑定（INTERO_ATTACHMENT）"认得"他。 |
| **训练回收（Harvest）** | 会话结束时评估其 `learned_bias` 增量，达标则收入训练池。 |
| **合并（Merge）** | 训练池经 EMA 合并进主体 `learned_bias`，让主体偏置（prediction_familiarity / action_suppression / vocal_efficacy / 曲线）成长。 |
| **能力探针（Capability Probe）** | 能力课程治理器的逐层开门信号（编码器→深度→关系→注意力→好奇）。 |

## 5. 功能需求

### F1. 主体 AI 常驻成长引擎 ★最高优先

**目标**：一个永不停机、持续被喂养、持续吸收全平台经验的主模型。

**F1.1 常驻主体进程**
- 独立 systemd 服务 `aborn-prime`，与访客 gateway 解耦，崩溃自动重启。
- 自己的 runtime 目录（热盘），其 `learned_bias.bin` 即全局 master。
- 7×24 存活；reserve 经济须先修稳（见 F1.4），否则会"饿死"进 Standby。

**F1.2 课程喂养（Nursery）**
- 内置发声/感知课程喂养器（已实现 `nursery_feeder.mjs`：合成频带帧、占空比、无 TTS）。
- 课程随能力探针推进（由简到难：单音→音对→节奏→呼应→词→句；视觉：单色块→运动→物件）。
- 喂养强度自适应 reserve（饿了少喂、饱了多教）。

**F1.3 吸收全平台经验**
- 定期把训练池（F2）EMA 合并进主体 `learned_bias`，让其偏置成长。
- 合并保留主体人格连续性（小步长 EMA，噪声门），不被单次会话主导。

**F1.4 生存平衡修复（前置阻塞）**
- 修复 reserve 在连续刺激下崩溃的问题：生存门提前介入（高 reserve 即限发声）/ 调发声 exertion / 课程占空比。
- 验收：主体在连续喂养下 reserve 稳定在健康带（不长期 Standby），`n_prototypes` 能持续 >0。

**F1.5 主体可观测**
- 暴露主体生命指标（reserve、能力探针、原型数、合并次数）到一个内部 `/admin/prime/status` 路由 + 日志。

**验收标准**
- `master_learned_bias.bin` 持续更新（mtime 滚动）。
- 主体连续存活 ≥7 天无人工干预。
- 能力探针随时间单调上行（周维度）。

---

### F2. 分布式训练成果回收 ★高优先

**目标**：让每一次互动——匿名或注册——都喂养主体成长。

**F2.1 会话级回收**
- 每个会话关闭时运行 `evaluate_session`，达标则 `collect_to_pool`。
- **放宽质量门**：当前 ≥5 分钟过严。改为：有效感知事件数 + bias 真实增量为主，时长为辅；支持**增量回收**（短会话也可贡献其 delta）。

**F2.2 匿名 vs 注册回收策略**
- **匿名会话**：仅回收通用经验（`learned_bias` 通用部分），不涉个人数据。关闭即回收即销毁。
- **注册用户**：
  - 个人记忆（面孔/声音/主人绑定）留在其命名空间，**不进主体**。
  - 通用学习成果**定期**回收进主体（与匿名同池，EMA 合并）。

**F2.3 合并管线**
- 训练池 → 主体的 EMA 合并（已实现 `merge_pool`，需接到常驻主体而非静态文件）。
- 周期可配置；合并前去重/质量加权。

**F2.4 隐私边界**
- 进主体的只有"去个人化的通用偏置"（曲线/familiarity/vocal_efficacy 等数值），**绝不含**原始音视频、面孔指纹、邮箱手机。

**验收标准**
- 训练池在有访客时持续有新文件进出。
- 合并日志显示主体 bias 在更新。
- 个人数据从不出现在主体 runtime。

---

### F3. 账号认证（极简，国内可用）

**目标**：30 秒内完成注册，零繁杂手续。

**F3.1 认证方式（二选一）**
- **手机短信验证码**（国内主流，优先）：对接国内短信服务商（阿里云/腾讯云短信）。
- **邮箱验证码**：已有 SMTP 后端（`auth.mjs`）。
- 二者复用已实现的 OTP 后端（`identity.mjs` + `phone_auth.mjs`）。

**F3.2 极简注册流程**
1. 输入手机号/邮箱 → 收验证码
2. 填验证码 → 验证通过
3. **给实例起个名字** → 完成
- 不要密码、不要邮箱二次确认、不要问卷、不要协议长文（仅一行同意采集训练成果的勾选，合规底线）。

**F3.3 唯一性与找回**
- 一个手机号/邮箱 = 一个实例（已实现唯一性约束）。
- 找回 = 重新验证码登录（无密码即无需找回密码）。

**验收标准**
- 从落地页到"实例已创建"≤30 秒、≤3 次输入。

### F4. 网页端：访客直入 + 登录引导

**目标**：零门槛参与；登录是"升级"而非"门槛"。

**F4.1 落地页（首页）**
- 主按钮：**「直接进入，开始陪它」**（访客模式，无需登录）。
- 次级引导卡：**「登录后，它会成为你的——记得你的脸、你的声音，认你为主人」**（解释登录价值）。
- 极简、安静的视觉（延续现有 commune 美学）。

**F4.2 访客模式**
- 点击即请求摄像头/麦克风 → 直连临时 body → 开始互动。
- 关闭页面 → 成果回收 → 会话销毁。
- 可选：访客可随时点"登录保存"，把当前进展转为专属实例。

**F4.3 登录/注册流（F3 的前端）**
- 手机号/邮箱输入 → 验证码 → 起名 → 进入专属实例。
- 复用已 live 的 `/auth/*` 与 `/instances` 路由。

**F4.4 专属实例界面**
- 顶部显示实例名 + "它认得你"状态（识别置信度的柔和提示）。
- 与访客界面一致的共处体验，但记忆跨会话延续。

**F4.5 多语言**
- 中/英（已有 i18n 基础）。

**验收标准**
- 访客 0 点击登录即可开始。
- 登录用户重连后实例延续上次记忆。

### F5. 主人识别（面孔 + 声音绑定）

**目标**：登录用户的实例"认得"他——这是登录的核心情感价值。

**F5.1 主人指纹**
- 复用 `familiar_objects`（视觉指纹）+ VIB 声音指纹 + 责任人绑定（INTERO_ATTACHMENT / 责任人机制）。
- 注册时/早期几次会话采集主人的面孔（Gaussian 场/视觉）与声音特征，绑定到该实例命名空间。

**F5.2 再识别**
- 主人回来时，实例通过面孔+声音匹配 → 提升 attachment（"亲近感"）→ 行为上更亲昵/响应更强。
- 识别是**涌现的**（familiar_objects 的熟悉度累积），不是人脸数据库比对。

**F5.3 隐私**
- 面孔/声音指纹只存于该用户命名空间（脱敏、本地），不进主体、不外传。
- 用户可一键删除其实例与所有个人数据。

**验收标准**
- 同一用户多次会话后，实例对其 attachment 显著高于陌生人。

### F6. 能力发展目标（课程治理）

**目标**：尽可能早地长出理解、交流、视觉/听觉识别、空间、物件能力。

**F6.1 能力维度与对应机制**
| 能力 | 对应子系统 | 当前状态 |
|------|-----------|---------|
| 交流（发声/语言） | 发声模仿环路 + 语言绑定 | ✅ 环路已通，学步中 |
| 听觉识别 | VIB 频带 + familiar_objects 音频指纹 | ✅ 事件提名已修 |
| 视觉识别 | Gaussian 视觉场 + 物件槽 | ✅ 场已接，识别待长 |
| 空间感知 | 主动感知/虚拟脖子 + 逆深度 ρ | ⚠️ 孤岛，待接线 |
| 基础物件 | 物件槽 + 高斯簇（common-fate） | ⚠️ 待 Gaussian 成熟 |
| 理解 | VPC 跨层信用分配 + 关系图 | 拱心石，长期 |

**F6.2 能力课程治理器**
- 逐层探针开门（编码器→深度→关系→注意力→好奇），拆联合自举，避免收敛塌缩。
- 当前治理器为未接线空壳，需真正接入主循环门控（延续既有补救计划）。

**F6.3 空间能力前置**
- 静止单目病态 → 深度只来自平移。网页端已有"请给它看运动物体/推远拉近手机"提示作"脖子"替身；后续上虚拟脖子主动感知。

**验收标准**
- 每个能力维度有一个可读探针，周维度上行。

### F7. 感知升级——视觉分辨率提升 ★（认物识人的物质基础）

> **诚实基线（2026-06-05 代码实测）**：当前浏览器传给 body 的是 **32×24 灰度网格（768 像素，无色彩）**，Gaussian 场重建分辨率 48×36。这个分辨率相当于把摄像头画面压缩成一张邮票大小的黑白图——人脸只有几个像素，物体轮廓无从辨别，是视觉识别能力的根本瓶颈。

#### F7.1 视觉分辨率路线图

**三档升级，按 CPU 和 GPU 负担分阶段实施：**

| 阶段 | 浏览器发送网格 | 颜色 | 传输量/帧 | Gaussian 场 | 触发条件 |
|------|-------------|------|---------|------------|---------|
| **当前** | 32×24 | 灰度 | ~3KB | 48×36 | 已部署 |
| **L1（立即）** | 96×72 | 灰度 | ~27KB | 96×72 | CPU 可承受 |
| **L2（M3 GPU 后）** | 96×72 + 32×24 RGB | 灰度+色彩 | ~39KB | 96×72 彩色 | GPU 驱动 Gaussian |
| **L3（长期）** | 128×96 RGB | 全彩 | ~49KB | 128×96 + 多尺度 | GPU 批处理成熟 |

> 移动端带宽预算：L1 帧 27KB × 20Hz = 540KB/s（WiFi 轻松，4G 可接受）。L2/L3 需 WiFi 环境。

**F7.1.1 L1 实施细节（立即可做，纯 CPU）**

- **浏览器端**（`perception.ts`）：把采样画布从 32×24 升到 96×72，同一路线只传 luma
- **帧格式**（`net_adapter.rs`）：`GRID_W = 96, GRID_H = 72`，帧字节从 3137 → 27713
  - 相应更新 `security.mjs` 的 `SENSES_FRAME_BYTES` 和 `Commune.tsx` 的 `FRAME_BYTES`
- **Gaussian 场**（`phot_gaussian.rs`）：`GAUSS_REC_W/H` 升到 96×72，`GAUSS_CAP` 从 64 → 128
- **物件槽感知**（`net_adapter.rs` `NetSensesAdapter::tick()`）：把 2×2 区域感知升到 4×4（16 个区域，每区域 5 轴），触发更细粒度的物体追踪

**F7.1.2 L2 彩色（M3 后，GPU 驱动）**

- 浏览器同时发送 luma 96×72 + RGB 32×24（合并为同一帧追加字段）
- Gaussian 场增加 RGB 三通道（不再纯灰度），`tick_gaussian_field_from_net` 扩为彩色输入
- surface 输出颜色从灰度→真实色彩，视觉外化更自然

**F7.2 涌现红线**
- 提升分辨率 = **扩大感知输入的物理范围**，不引入语义标签。
- Gaussian 场的颜色学习仍是本地 Widrow-Hoff 规则，不使用预训练编码器。
- 不添加任何目标检测 API（如 TensorFlow.js COCO），AI 自己学出物体。

**验收标准**
- 同一用户的脸在 L1 分辨率下，Gaussian 场能形成稳定的高斯聚类（`active_count` >10 且位置稳定）。
- `n_prototypes` 在有用户互动时增长速度 > 当前 L0 的 3 倍（更多像素 → 更多预测误差 → 更快学习）。

### F8. 感知升级——听觉分辨率提升 ★

> **诚实基线**：浏览器发 **12 个粗频带**，body 内部再压成 **4 带**。12 带覆盖约每个 octave 一个格，无法区分元音（formant 需要 300–3000Hz 精细分辨）、无法识别音色差异。4 带则连男女声都难区分。

**F8.1 浏览器端升级（`perception.ts`）**

把 `AnalyserNode` 的 FFT 从当前配置改为 256-bin，提取 **32 频带**（mel-scale 近似，物理先验，不是 ML）：

```
频带分布（mel-scale，物理先验）：
  B0–B7:  低频（80–500Hz，男女声基频、低元音）
  B8–B19: 中频（500–3000Hz，主要元音共振峰 F1/F2/F3）
  B20–B27: 高频（3k–8kHz，辅音摩擦音、声母）
  B28–B31: 超高（8k–20kHz，气息音、嘶声）
```

新增 4 个时频特征随帧附送：
- `spectral_centroid`：频谱重心，反映"音色明亮度"
- `spectral_flux`：帧间频谱变化（比 audio_flux 更细）
- `zero_crossing_rate`：过零率，辅音/噪声识别
- `harmonic_ratio`：谐波/噪声比（区分清音/浊音）

**帧格式变化**（帧略微变大，仍在合理范围）：
```
新 BANDS = 32，新辅助特征 = 4
帧字节增量 = (32-12)*4 + 4*4 = 96 bytes
```

**F8.2 体内升级（`net_adapter.rs`，`vib.rs`）**

- `VIB_BANDS` 从 4 → **8**（提升内部频率分辨率）
- `NetSensesAdapter::tick()` 把 32 浏览器频带映射到 8 内部 VIB 轴（每 4 带平均）
- `familiar_objects` 音频指纹从 4 维 → **8 维**，音色识别能力提升约 2×

**验收标准**
- body 可区分男声/女声（不同性别说话时，VIB 前 4 轴 vs 后 4 轴权重差异 >0.3）。
- 主人绑定（F5）的声音匹配置信度 > 当前 4 带版本提升 >20%。

### F9. 发声升级——生物型声音合成 ★★

> **诚实基线**：当前发声是三个纯正弦波叠加：`sin(2πft) + 0.3·sin(4πft) + 0.1·sin(6πft)`。这是最基础的加法合成，听起来像老式电子游戏的"哔哔"声。生物声音的特征——声带的非线性振动、呼吸噪声、颤音、细微音量起伏——全部缺失。

**F9.1 生物声音的三要素（纯信号处理，无需 ML）**

```
生物声音 = 声门源（glottal source）× 声道滤波器 + 气息噪声
         ↑ 声带振动的非线性波形    ↑ 共振峰塑形         ↑ 有机纹理
```

**F9.2 实施方案（纯 Rust，无外部库）**

**① 声门源替换（最大收益）**

把纯正弦替换为 **Rosenberg-C 声门脉冲**近似：
```rust
// 当前（机械）:
let f = sin(2πft) + 0.3*sin(4πft) + 0.1*resonance*sin(6πft)

// 升级（生物）: Rosenberg-C 近似
// 开相（t ∈ [0, T_open]）: raised-cosine 上升
// 关相（t ∈ [T_open, T_close]）: 快速下降（声门关闭冲击）
// 闭相（t ∈ [T_close, T_period]）: 静默（空气流停止）
let oq = 0.6 + 0.2 * organ.pitch_tension  // 开商（open quotient）
let g = rosenberg_c(t_in_period, oq)       // 非线性脉冲，有丰富谐波
```

视觉效果：波形从平滑正弦 → 带尖峰的锯齿形脉冲（人声的真实形态）。

**② 声道共振峰滤波器（元音塑形）**

用两个 **2 极 IIR 共振峰滤波器** 模拟 F1（500–900Hz）和 F2（1000–2500Hz）：
```rust
// resonance_position [0,1] → 元音空间
// 0.0 = 类"啊" (高F1, 低F2)  ← 开口大、后舌
// 0.5 = 类"鹅" (中F1, 中F2)
// 1.0 = 类"伊" (低F1, 高F2)  ← 开口小、前舌
let f1 = 500.0 + organ.resonance_position * 400.0   // Hz
let f2 = 1000.0 + organ.resonance_position * 1500.0 // Hz
let out = formant_filter_2pole(g, f1, sample_rate)
let out = formant_filter_2pole(out, f2, sample_rate)
```

**③ 有机纹理（颤音 + 抖动 + 气息）**

```rust
// 颤音 vibrato: 基频 ±0.5% 以 ~5Hz 调制
let vibrato = 1.0 + 0.005 * sin(2π × 5.0 × t_global)
let pitch_modulated = pitch * vibrato

// 微抖 jitter: 每周期随机 ±1% 频率扰动（声带质量不均）
let jitter = 1.0 + rng.range(-0.01, 0.01)

// 微颤 shimmer: 每周期随机 ±3% 幅度扰动
let shimmer = 1.0 + rng.range(-0.03, 0.03)

// 气息噪声: 从 noise_mix 参数控制
let aspiration = pink_noise() * organ.noise_mix * 0.15
let out = (out * shimmer + aspiration).clamp(-1, 1)
```

**④ 呼吸包络（起音/收音）**

身体说话时有自然的起伏，不是恒幅：
```rust
// 接在 begin_voicing / tick_decay 上
// 起音: 10ms 内从 0 缓升到 breath_drive（指数攻击）
// 收音: breath_drive 归零时 20ms 内渐消（指数衰减）
```

**F9.3 参数映射（body 内部状态 → 声音参数）**

| body 参数 | 声音含义 | 范围 |
|-----------|---------|------|
| `breath_drive` | 响度（总幅度）| 0–1 |
| `pitch_tension` | 基频 F0 | 180–700Hz（婴儿高→成人低） |
| `resonance_position` | 元音空间（F1/F2 共振峰）| "啊"↔"伊" |
| `noise_mix` | 气息/嘶声比例 | 0=清晰 1=全气 |
| vitality `reserve` | 声音活力（影响颤音深度）| 低→颤音减弱 |

**F9.4 不违反涌现红线**
- 上述全部是**物理声学先验**（声带振动物理、共振腔声学），不是语义标签、不是预训练声码器。
- 没有文字转语音（TTS）、没有神经网络声码器（WaveNet/HiFiGAN）。
- AI 自己通过模仿学习调整这些物理参数，从而发出越来越接近它听到的声音。

**验收标准**
- 在安静环境中，听众能区分"这是有生命感的声音"而不是"这是合成器音调"（主观 MOS 评分 >3/5）。
- 不同 `resonance_position` 下发音明显不同（可量化：相邻元音的频谱重心差 >200Hz）。
- 声音在 body 健康时更响亮/有颤音，在 Standby 时减弱（生存与声音的联动）。

## 6. 基础设施需求

### I1. GPU 加速架构 ★（推广前必须）

**问题**：当前 100% CPU 标量；每个访客 = 一个 CPU body 进程；推广后并发 CPU 扛不住。RTX 3060 完全闲置。

**I1.1 主体优先上 GPU**
- 常驻主体 7×24 跑，是最值得 GPU 化的负载。优先把它的热路径迁 GPU。

**I1.2 热路径识别与迁移**
- 候选热点：Gaussian 泼溅/残差（逐元素独立，天然并行）、AR 预测器（全轴）、substrate 逐轴运算。
- 迁移技术选型：**wgpu compute shader**（splat 非标准张量算子，candle 无此原语；自定义 shader 更合适）。延续既有"CPU-first 写对、按 GPU 形状（SoA、无顺序依赖）组织、撞吞吐墙再机械移植"的决策。
- CPU 参考实现作为 GPU 数值对照基准保留。

**I1.3 多 body 批处理**
- 探索单 GPU 上批量推进多个访客 body 的同构计算（共享 shader，按实例批维度并行），把 N 个 CPU 进程压成 GPU 批。

**I1.4 容量模型**
- 定义"1 GPU 可承载 N 并发 body"的容量公式，驱动 `resourceGovernor` 的上限（替代当前固定 8）。

**验收标准**
- 主体主循环热路径在 GPU 上运行，CPU 占用显著下降。
- 单机并发 body 数较纯 CPU 提升数倍。

---

### I2. 存储分层与扩容 ★（简单高收益）

**现状**：`/` 82% 满是假象——同盘 828G 未分配、`/data` 915G 空、3.6T HDD 未用。

**I2.1 立即扩容系统盘**
- 用 `nvme1n1p3` 未分配的 ~828G 扩 LVM `ubuntu-vg/ubuntu-lv` + `resize2fs`，把 `/` 从 100G 扩到 ~900G。解燃眉。

**I2.2 冷热分层**
| 层 | 介质 | 内容 |
|----|------|------|
| 热 | SSD `/`（扩容后） | 主体 runtime、活跃会话、master_learned_bias |
| 温 | SSD `/data`（915G 空） | 训练池、用户命名空间记忆 |
| 冷 | HDD `sda` 3.6T（重新格式化 ext4 挂载） | 会话归档、快照历史、日志轮转 |

**I2.3 定期清理**
- 定时任务：清理超期 `/tmp/aborn-sessions`、轮转 gateway 日志、归档旧快照到 HDD、训练池超期文件按既有 `maxPoolAgeDays` 清。
- 监控告警：任一分区 >85% 告警。

**验收标准**
- `/` 使用率 <50%。
- 三层各司其职，清理任务自动运行。

## 10. 开放问题与决策点

1. **国内短信服务商**：阿里云短信 vs 腾讯云短信？（需实名+签名报备，约 1–3 天审核）

8. **数据合规**：训练成果采集的用户告知如何措辞（极简但合规）？
